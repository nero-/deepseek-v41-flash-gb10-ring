# Follow-up performance experiments

User authorized trying all six brainstormed directions, ordered by likelihood
of useful improvement. Correctness and end-to-end measurements selected
`engram-adaptive4k-query-indexer`. The previous permanent `engram-adaptive4k`
configuration was retained throughout screening and backed up during promotion.

1. Context-conditioned native verification costs: startup cost tables at 8K,
   64K and 256K, selected from the current request context. Native graph padding,
   confidence estimation, proposal distributions and rejection remain intact.
   This first stage measures context effects, not live cost learning.
2. Time-budgeted prefill: initial schedule-to-output controller was rejected
   for excessive first-token delay. Revision 2 measures intervals between
   completed steps, subtracts a smoothed decode baseline, and caps contention
   at 4K within the ordinary 8K allocation. Initial target 0.8 seconds.
3. Context-axis indexer TP: split candidate-free context scoring across four
   ranks and merge local top-k candidates. First require exact original
   selection; follow up with a local-score oracle if existing replicas differ.
4. Engram read-ahead: first isolate buffered I/O, then add bounded CPU advice
   for the next known prompt chunk. Original direct I/O bypasses page cache;
   advisory reads cannot benefit it. GPU consumption synchronization unchanged.
5. Owned-row prefill: first test native mHC row slicing with exact guards and
   reconstruct at boundaries. This is a prerequisite feasibility experiment,
   followed by retained ownership only if the native row-slice gate passes.
6. DSpark shortlist: retain original NVFP4 Markov rows and adapt the native
   gathered Markov kernel plus proposal sampler/cache to DeepSeek. Unlike the
   prior final-logit filter, this actually skips most Markov projection rows.

## Final qualification contract

The request-armed candidate must start with optimization disabled throughout
startup and CUDA graph capture, then pass its numerical guards after a real
request. It is tested at a 128-row minimum (normal decode has at most 96 rows
with this profile), with the candidate-free prefill and 8,192-compressed-position
conditions unchanged. The seven functional probes use approximately 94K prompt
tokens each and require at least 65,536 uncached tokens. The separate under-load
retrieval round uses similarly long prompts. The ordinary three-round ~29K
mixed-traffic workload remains unchanged for baseline latency comparison.
The return baseline's earlier long-functional wrapper used ~30K prompts; its
results are not a matched latency comparison with these longer quality probes.

Cold retrieval means zero prompt KV-cache reuse; it does not mean an empty
operating-system file cache. All comparisons use the same pinned checkpoint
and target precision. Different legal tied index selections can change output;
finite exact-score guards and task checks do not prove universal equivalence.

The first request-armed startup attempt was rejected before qualification:
`add_requests` also receives synthetic sampler warmups. The corrected gate
wraps the complete worker warmup method and only observes requests after that
method returns. Its CPU regression covers synthetic-input exclusion, original
call/return preservation, one-time real activation and reset across a second
warmup. GPU qualification requires the log order: worker warmup complete,
first real request, numerical guard.
